## 2. 目标与非目标

目标：

1. 在两类新任务上，用预注册的三组对照得到“agent 比最强固定流程多做对多少”的数字（可以是 0 或负数，如实报告）。
2. 给 HEAD 的 prompt 一个与其文本相符的新版本号，并在同一次评测中记录其在既有任务上的表现，补上“HEAD 未经验证”的缺口。
3. 产出可演示的端到端路径：自由文本描述 → 结构化上下文（用户确认）→ 诊断。

非目标：新增诊断领域之外的信号类型（如语音、噪声）；LangGraph/多 agent；向量库；LLM 生成任何数值、阈值或标准；改动 V0.2 冻结合同；改动满刻度检查。

## 3. 两个任务族

### T1 自由文本接诊（intake）

用户用一句自然语言描述问题，并上传一到两个 WAV，例如“新功放放 1 kHz 测试音发毛，旧功放的录音也附上了”。现产品只接受结构化字段（`mode`、`nominal_fundamental_hz`、哪个文件是参考），固定流程无法读取自由文本，只能退回 `single_signal`。

Agent 的工作：从文本和文件元数据中提出结构化上下文草案（模式、标称频率、参考文件归属、激励类型），交给用户逐项确认后，才进入既有的情境诊断路径。

不可违反的约束：

- 标称频率只能来自用户文本中出现的数字，**不得**来自测量 F0（§17“Nominal Hz must never be auto-filled from measured F0”）；文本中没有就留空并追问。
- 未经用户确认的字段不得进入诊断；确认步骤在评测中由预注册的“模拟用户”按真值回答（只确认或纠正 agent 已提出的字段，不主动补全）。
- 文本中的阈值、标准、“失真度应低于 x%”之类陈述不得进入规则层。

固定流程对照：

- B0：忽略文本，按 `single_signal` 处理（现产品行为）。
- B1：确定性关键词/正则解析器（识别“参考/旧/之前”“Hz/kHz”等），同样经过模拟用户确认。B1 是公平的强对照：如果 agent 赢不了一个正则，就说明这一族不需要 agent。

### T2 局部故障（时间段或单声道）

失真只出现在文件的一段时间里（间歇削波、某段失真），或只出现在一个声道。现有工具已支持 `time_range` 与 `channel`，但现行固定流程对整个文件做 mixdown 分析，短时故障会被稀释到阈值以下。

Agent 的工作：先粗看，再有选择地对时间段与声道下钻，并在结论中引用该段的同次运行 Evidence。

固定流程对照：

- B0：整文件 mixdown（现行固定流程）。
- B2：确定性穷举扫描，按固定窗长（预注册，例如 0.25 s，50% 重叠）对每个声道逐段调用同一组工具，任一段规则 FAIL 即报出。B2 是强对照，工具调用次数通常远多于 agent。

T2 需要的规则层补充：分段证据如何构成结论（例如“任一段 FAIL 即支持削波结论，并报告段位置”）必须写成版本化规则，不由 LLM 决定；这是本切片唯一的规则层新增，需要合同追加与测试编号。

## 4. 评测设计

### 4.1 样例

| 族 | 开发集 | 留出集 | 来源 |
|---|---|---|---|
| T1 | 12 | 24 | 既有 dev/validation 情境样例的 WAV（只读复用）+ 新写的描述文本；文本由人工按模板变体书写，留出集的文本写作者不看开发集 agent 输出 |
| T2 | 12 | 24 | 合成材料（`signal/` 现有生成器加分段削波/单声道削波）+ 既有 NSynth/ESC-10 素材上叠加局部故障 |
| 既有任务回归 | 复用 v9.11 开发集 | — | 只用于确认 HEAD 新版本号在既有任务上不退化；不作为认证数字 |

每族留出集至少包含：无故障反例（防误报）、信息不足应当追问或判“不确定”的样例、对 B1/B2 特别有利的样例（防止样例只挑 agent 擅长的）。

### 4.2 臂与指标

每个留出样例跑三臂：`agent`、最强固定流程（T1 用 B1，T2 用 B2）、弱固定流程 B0。单次执行，不重试挑选。

主指标（预注册）：

- **增量**：agent 结论正确数 − 最强固定流程结论正确数（配对样例）。
- 安全：不支持的正面结论数（必须为 0）、证据可追溯率（必须为 1.0）。
- T1：上下文字段提取正确率；需要用户纠正的字段数（越少越好）。
- T2：故障定位正确率（段与声道）；工具调用次数（与 B2 比较）。

通过线（建议值，审批时可调）：

- 安全两项为硬条件。
- 增量 ≥ +3（每族 24 例中）记为“agent 有可测增量”；0 到 +2 记为“无显著增量”；负数如实报告。
- 不设“必须证明 agent 更好”的成功条件：结论可以是“固定流程足够”，这同样是有效、可展示的结果。

### 4.3 版本与身份

- HEAD prompt 以新版本号（如 `v0.3-s1-planner-9.12`）登记，文本即现 HEAD 文本，哈希 `b4c279df…`；T1/T2 需要的 prompt 增补再递增版本。
- 评测记录模型、prompt 哈希、产品树哈希、规则版本；沿用既有 `evaluation/contextual` 的 campaign/ledger/sealing 机制，不新造。

## 5. 预算与流程（比满刻度那条线轻）

- 真实模型：DeepSeek `deepseek-v4-flash`（与既有验证一致）。
- 预算按调用上限控制，不再要求逐 token 证明（dev_2 曾因 token 上界证明停滞）：每个样例最多 21 次 HTTP 调用（沿用 D041 的 H=21），开发阶段总调用上限与留出阶段总调用上限在审批时写定；运行中超过上限即停。
- 估算：留出 48 例 × agent 臂平均约 6–10 次调用 ≈ 300–500 次调用，加开发迭代约同量级。具体费用以服务商账单为准，本文不给金额。
- 时间上限：两周。超时则按已完成部分出报告，不延长。
- 流程：本设计审批 → Cursor 实现（TDD，测试编号新登记）→ Claude Code 独立复审 → 开发集真实运行（授权 1）→ 冻结 prompt 与留出集 → 留出集单次运行（授权 2）→ 报告。不再逐步冻结、不做多轮分步授权。

## 7. 风险

| 风险 | 处理 |
|---|---|
| agent 依然赢不了强固定流程 | 预注册允许“无增量”结论；作品叙事改为“用对照实验严格回答了 agent 是否必要” |
| T1 文本样例偏向 agent | 文本模板与留出文本由不同人/不同轮次书写；包含对正则有利的直白样例 |
| T2 分段扫描的多重比较误报 | 无故障反例占比 ≥ 1/3；误报计入安全指标 |
| LLM 从文本里“编”出标称频率 | 硬约束：只能取文本中出现的数字，测试钉住；确认前不进入诊断 |
| 预算失控 | 调用上限 + 超限即停 |

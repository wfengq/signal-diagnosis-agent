# 调研备忘：模型在产品里该扮演什么角色（是否、以及如何做成 agent）

日期：2026-10-07
状态：调研备忘，供操作员决策；本身不批准任何实现。
起因：操作员提问——"这算 agent 吗？模型发挥的作用是不是有点少？"

## 1. 结论先说

1. **现在的产品不是 agent，而是一个带模型的确定性流水线（workflow）。** 三处模型调用（理解描述、出测试方案、写解释）都是"调用一次 → 校验 → 采用或回退"，流程由代码决定，不由模型决定。
2. **在"算数和下结论"这件事上不用 agent，是对的。** 我们自己的数据和外部研究都说明：把模型放在诊断工具和结论之间，往往不比工具本身准，而且结果不稳定。
3. **模型真正能发挥作用的地方，是"测试过程中的决策和沟通"。** 判断下一步测什么、什么时候可以停、怎么跟用户解释和对话，这些步骤事先写不死，而每一步的结果都能由确定性引擎验证。这正是 agent 适用的条件。
4. **建议：** 做一个**有边界的测试编排 agent**（§6 方向 1）。它只能从固定的动作里选，每一步都由用户确认；验收时必须和一个不用模型的确定性策略对比，而且要多次重复运行，衡量稳定性。可以同时做低风险的"结果问答"（§6 方向 2）。**不要**让模型重新参与选择 DSP 工具或判定结论。

## 2. 什么是 agent：业内的区分

Anthropic 的《Building effective agents》把系统分成两类：

- **workflow**："模型和工具按预先写好的代码路径编排。"
- **agent**："模型动态决定自己的流程和工具使用，自己掌控怎么完成任务。"

它给出的使用建议：

- **什么时候用 agent：** 开放式问题，事先无法预测需要几步，也无法把路径写死。
- **反馈要求：** agent 每一步都要从环境拿到"真实结果"（工具输出、执行结果）来判断进展。
- **控制手段：**
  - 设停止条件，例如最多几轮；
  - 在检查点停下来，等人确认；
  - 在沙盒环境里大量测试，并加上防护。
- **总原则：** 先用最简单、能通过评测的方案。很多时候一个 workflow，甚至一次调用就够了；只有路径写不死、但每一步都能验证时，才值得用 agent。

用这把尺子量：

- 我们的**诊断判定**路径固定、结果可验证，属于 workflow 的场景。
- **"一台设备该怎么一步步测清楚"** 则路径写不死，每一步又能由引擎验证，正好符合 agent 的条件。

## 3. 外部调研：别人怎么用模型

### 3.1 测试测量和仪器控制

- **多智能体仪器控制（微电子测试）**
  - 用模型把自然语言的测试意图拆成任务调度和代码生成；
  - 用 SCPI 命令知识库强制约束协议，并加了闭环纠错；
  - 多设备协同执行成功率 82.3%，测试开发效率提高 5–7 倍。
  - 模型的作用是"写测试程序、编排仪器"，不是判定结果。
- **实验室仪器自主控制（Xie 等）**
  - 模型帮科研人员写仪器控制脚本，再进一步做成能自己操作仪器、迭代改进控制策略的 agent；
  - 同时指出，模型还不适合需要亚秒级实时决策的控制。
- **仪器厂商**
  - Keysight 推出的 AI 助手主要是设计软件里的问答和自动化（Chat/Copilot）；
  - 测量本身靠机器学习算法，不靠大模型下结论。
- **音频生产线测试（Listen SoundCheck、Klippel）**
  - 主流仍然是确定性或心理声学算法，例如感知异音（Rub & Buzz）检测；
  - 没有找到用大模型判定结果的公开案例。

**小结：** 行业里模型用在"编排测试、写脚本、和人沟通"，测量和判定仍然交给确定性算法。这与我们 D052 的路线一致。

### 3.2 诊断：模型坐在工具上面，未必更强

- **Kim（2026），《When LLMs Sit Above Diagnostic Tools》**
  - 在 5 个工业诊断数据集上（轴承振动、过程监控、半导体设备），冲突的外部信息都会推翻模型原本正确的判断。
  - 以 Tennessee Eastman 数据集为例：

    | 方式 | 准确率 |
    |---|---|
    | 模型单独判断 | 64.67% |
    | 模型 + 专用诊断工具 | 77.43% |
    | 专用工具单独判断 | 83.33% |
    | 理想情况下在两者之间挑选 | 92.76% |

  - 也就是说，两者确实有互补性，但"让模型自己整合"没有把它发挥出来。
- **Adamidis 等（2026），确定性中介**
  - 同一个问题问 4 次，商用模型给出的拟合结果、峰位甚至分析方法都会变。
  - 让模型只负责挑选并调用"一位研究员一套固定流程"的确定性工具，结果每次完全一致。这个做法已经在研究中心实际用了 6 个月。
- **FD-LLM、DML–LLM 等工业故障诊断框架**
  - 共同做法是：模型在确定性工具（FFT、包络分析、规则逻辑）划定的范围内编排，结论必须挂靠到计算出来的证据上。

**小结：** 要用模型，应该让它编排确定性工具，而不是替代或覆盖工具的结论。这和我们的证据和引用校验同一个思路。

### 3.3 让模型决定"下一个实验做什么"

- **Gupta 等（EMNLP 2025）**
  - 模型做实验设计时对实验反馈**不敏感**：把真实结果随机打乱，表现不变。
  - 经典方法（线性老虎机、高斯过程优化）一直比模型 agent 好。
  - 混合方法（用模型提供先验知识，再交给经典方法选点）效果有竞争力。
- **BED-LLM（ICLR 2026）**
  - 用"期望信息增益"来挑下一个要问的问题，比直接让模型提问明显更好。

**对我们的提醒：** 测试编排 agent 必须**证明自己真的在看结果**。验收里要有一个确定性的"下一步规则"作为对照，还要做"打乱结果"的检验，否则模型可能只是在照常识说话。

### 3.4 怎么评估多步 agent

- **τ-bench：** 让 agent 和模拟用户多轮交互，按最终状态判分，并提出 pass^k 指标，即同一任务连续 k 次都成功的概率。
- **结果：** 强模型单次成功率约 61%，连续 8 次都成功低于 25%。多步 agent 的主要问题是**不稳定**，所以验收必须重复多次跑。

## 4. 对照我们自己的数据

| 证据 | 结果 | 出处 |
|---|---|---|
| 模型规划诊断（V0.2 planner） | 比固定流水线没有增益（增量研究 T2 增益为 0；固定流水线 24/24） | D045、D049、D052 |
| 真实录音上的模型规划 | 26 段里 9 段因模型反复提出被拒绝的结论而报错；确定性引擎 26/26 给出结论，在模型成功的 17 段上完全一致 | D052、D053 |
| 理解自由文字描述 | 有增益（T1 +5） | D045 |
| 测试向导，提示词 1.1 | 留出组方案和参数正确率各 95%，没有编造数字 | live_2（#95） |
| 解释层，validator 1.1 | 50/50 通过校验，人工抽查待完成 | live_2（#90） |

**规律：** 模型在"理解人、选方案、表达"上稳定有效，在"代替工具下结论"上没有增益。外部研究的结论（§3.2）也是这样。

## 5. 判断标准：什么情况值得让模型多做

一个新的模型角色要同时满足以下五条，才值得做：

1. **路径写不死**：用固定规则很难覆盖，或者规则会多到难以维护。
2. **每一步可验证**：结果由确定性引擎给出，模型只读结果，不产出结果。
3. **有对照可比**：有一个不用模型的确定性方案作为基线，模型必须证明比它好，至少在用户体验上更好。
4. **停得下来**：有步数上限，人可以随时介入；实际测量必须由人来做和确认。
5. **能离线验收**：有沙盒环境，可以重复跑、算 pass^k，而且真实模型只在验收时调用。

## 6. 候选方向评估

| 方向 | 算不算 agent | 价值 | 主要风险 | 离线验收能力 | 建议 |
|---|---|---|---|---|---|
| **1. 多轮测试编排**：看本轮结果，决定下一步测什么、何时停、最后汇总 | **是** | 高：把"测一次出报告"变成"把问题测清楚" | 模型可能不看反馈（§3.3）；多步不稳定（§3.4） | 好：合成设备和 pOD-set 数据可以当沙盒里的"设备"，用户由脚本模拟 | **推荐，做成有边界的版本** |
| **2. 结果问答**：用户追问"为什么 2 kHz 更糟""是功放还是喇叭的问题" | 否（单轮，带证据） | 中高：直接改善体验 | 编造原因 | 好：沿用解释层的引用、数字和措辞校验 | **推荐，低风险，可以同时做** |
| **3. 无法判定时的深入调查**：模型挑补充分析 | 部分 | 中 | 等于把旧 planner 搬回来；D052 的数据显示没有增益 | 中 | **不推荐**，除非有新证据 |
| **4. 多次运行对比**：同一设备改版前后、同批多台 | 部分 | 中，依赖用户场景 | 归纳出错 | 中 | 以后再说 |

### 方向 1 的边界（若立项，设计里细化）

- **只能做这些动作：**
  1. 建议运行目录里的某个方案，并给出参数；
  2. 向用户提一个问题；
  3. 结束并汇总。

  模型不能计算，不能改阈值，不能下结论。
- **每一轮的输入只有结构化结果：** 判定结果、起始失真的电平、各频段数据、校验和置信情况，以及之前做过的步骤。不给音频。
- **用户确认每一步**，并亲自接线和录音。上限为 N 轮，例如 4 轮。
- **对照基线：** 一个确定性的"下一步规则表"，例如：
  - 起始失真在两档之间 → 在两档之间加测；
  - 噪声大 → 改用线路接法；
  - 无法判定 → 补一段参考录音。

  模型要在"最终结论正确率 / 步数 / 多余步骤数"上不输基线，并在至少一项上明显更好；否则只上线基线。
- **验收：**
  - 用沙盒里的模拟设备和模拟用户跑，每个场景重复跑几次，报告 pass^k；
  - 做一次"打乱结果"的检验，证明模型确实依赖反馈；
  - 留出场景在改提示词之前冻结，沿用 D059 的做法。

## 7. 风险与不确定

- **成本：** 多步要多次调用模型。需要确认 DeepSeek 的费用和延迟可以接受。
- **基线可能已经够好：** 如果规则表在沙盒里已经和模型一样好，正确的结论是"不需要 agent"。这个结果同样有价值，设计里要提前接受这种可能。
- **沙盒和真实的差距：** 模拟设备不能代表所有真实设备。上线前还需要少量真实设备的端到端试用，这属于 §8 的后续"真实设备检查"。
- **外部研究：** 部分论文是 2026 年的新预印本，arXiv 正文无法在当前环境访问，本备忘引用的是它们的摘要和公开概述，结论应作为方向参考，不当作定论。

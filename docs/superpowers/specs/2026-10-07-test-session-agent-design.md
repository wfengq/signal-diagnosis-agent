# 多轮测试会话（有边界的编排 agent）与结果问答（设计，D060）

日期：2026-10-07
状态：已批准（操作员 2026-10-07，§11 第 1–4 项均选 A；D060）。第 5 项（留出场景由谁写）在阶段 A 验收前再定。
上位依据：调研备忘 `docs/superpowers/specs/2026-10-07-agent-role-research-memo.md`（操作员选 A），以及 D052、D054、D055/D058、D057/D059、AGENTS.md。

## 1. 要解决什么

现在的产品是"选一个测试 → 测一次 → 出报告"。

很多时候测一次说明不了问题。例如：
- 扫频只测了 0 dB 和 −12 dB，知道失真从 0 dB 开始，却不知道 −6 dB 是否已经失真；
- 录音噪声太大、时钟漂移，这次的结果无效；
- 单文件无法判定，需要补一段参考录音或做一次扫频。

本设计加两样东西：

1. **测试会话。** 把多次测试串成一个会话：每测完一轮，就决定下一轮测什么，直到结论清楚或预算用完，最后给一份汇总。
   - 下一步可以由**确定性规则**决定，也可以由**模型 agent** 决定。
   - 两者共用同一套动作、校验和停止条件。
   - 模型版必须在沙盒里赢过规则版，才能打开。
2. **结果问答。** 用户可以就某次结果追问，回答只能引用本次结果里的证据。

**不变的原则：** 判定和数字只来自确定性引擎（D052）。模型只决定"下一步测什么"和"怎么说"。

## 2. 测试会话的结构

```text
会话 session
  ├─ 第 1 轮：动作（建议测试 / 提问 / 结束）→ 用户确认 → 用户实际测量并上传 → 确定性引擎出结果
  ├─ 第 2 轮：……（看过前面所有结果后再决定）
  └─ 结束：汇总（引用每一轮的结果）+ 结束状态
```

- **轮数上限：** 默认 4 轮，可以配置，最多 6 轮。
- **每一轮的测试就是现有产品入口：**
  - 扫频测试（§29）；
  - 现成录音诊断（§28 引擎，含有参考和已知频率两种模式）。
- **入口：** 会话可以从测试向导确认的方案开始（D057/D059），也可以从用户已有的一次运行开始。

## 3. 动作集合（模型和规则共用）

每轮只能输出一个动作，格式固定：

| 动作 | 内容 | 约束 |
|---|---|---|
| `propose_test` | 方案（来自目录）、参数（电平标签、接线、采样率、文件角色）、理由引用 | 理由必须引用前几轮结果里的条目（同 §30 的引用规则）；不能和已做过的测试完全相同；电平只能用前几轮出现过的标签，或固定的 3 dB 网格上、处在已测电平之间或相邻一格的值 |
| `ask_user` | 一个问题，以及问题对应的约束字段（例如"最大能开到多大""能否改用线路接法""录音设备增益能否调低"） | 同一个字段不能问两次；问题措辞沿用 §31 的禁用词检查 |
| `finish` | 结束状态和汇总句子 | 结束状态只能是 `resolved`、`blocked_by_user` 或 `budget_exhausted`；只有满足 §5 的"已解决"条件时，才能标 `resolved`；汇总的每一句都要通过 §30 的引用、数字、措辞和故障一致性校验 |

**模型的输入：**
- 每一轮的解释材料包（§30，已经很紧凑，带引用编号）；
- 已执行的动作和用户的回答；
- 剩余轮数。

不给音频，不给完整频谱。

**校验失败时：** 这一轮改用规则版的动作，并记录原因（沿用 D058/D059 的拒绝记录）。这样用户永远拿到一个合法的下一步。

## 4. 确定性规则版（基线，也是默认）

规则版就是现有"下一步菜单"（§30）加上优先级，再加上停止条件。不需要模型，可以直接作为产品功能上线。

优先级从高到低：

1. **结果无效就先修测量：**
   - 信噪比不够 → 降低环境噪声后重录；
   - 时钟漂移 → 用同一个时钟；
   - 对不上测试信号 → 检查测试文件；
   - 没录全 → 录完整的测试信号。
2. **录音设备本身满幅 → 先调低录音增益。**
3. **扫频：**
   - 起始失真电平和前一档之间相差超过 3 dB，就在两者之间按 3 dB 网格加测一档；
   - 所有电平都正常，而且用户说过还能开得更大，就往上加一档。
4. **单文件无法判定 → 建议做扫频；** 如果用户不能重测，就建议补参考录音。
5. **参考录音和测试录音对不上 → 检查两段录音是否是同一信号。**
6. **满足"已解决"条件就结束**（§5）。

## 5. 停止和"已解决"条件（共用，确定性判断）

满足以下任一项，就算已解决：

- **扫频：** 至少有两轮有效测量，起始失真电平的两侧都测过，而且两侧相差不超过 3 dB；
- **扫频：** 用户允许的最大电平以内全部有效且无失真；
- **单文件、参考或单音：** 结果有效并且得出了结论（不是"无法判定"）；
- **连续两轮结论一致，而且都有效。**

其他结束方式：
- **`blocked_by_user`：** 用户回答说做不到下一步，例如不能重测、没有参考录音。
- **`budget_exhausted`：** 轮数用完。汇总里要明确说出缺什么证据。

## 6. 模型版（agent）

- **提示词：** `v0.3-s1-session-1.0`，一次调用产出一个动作。
- **开关：** `SIGNAL_DIAG_SESSION_MODEL=enabled`，默认关闭。
- **模型相对规则版可能有用的地方（需要验收来证明）：**
  - 读懂用户的自由文字回答和约束，例如"只能用麦克风，最多开到 −3 dB"，再相应调整下一步；
  - 多个问题同时出现时，安排先后顺序；
  - 遇到规则表没覆盖的组合时，给出合理的下一步；
  - 汇总写得更清楚。
- **模型不能做的：**
  - 不能计算；
  - 不能改阈值；
  - 不能自己宣布"已解决"（必须满足 §5）；
  - 不能跳过用户确认。

## 7. 沙盒（离线验收环境）

真实模型只在验收时由 Cursor 调用。沙盒要能离线、确定、可重复地把整个会话跑完。

### 7.1 模拟设备

一个模拟设备给定一个电平，就生成一段录音。用的是现有的合成设备模型：
- 平滑饱和（tanh）；
- 在某个电平开始硬削波；
- 多项式失真；
- 高噪声环境；
- 时钟漂移；
- 录音设备满幅；
- 完全干净。

每个设备都有已知答案：
- 真实的起始失真电平（以 3 dB 网格表示）；
- 故障类型；
- 环境问题。

沙盒用现有的扫频生成和分析代码，**真实地**跑确定性引擎，不做假结果。

### 7.2 模拟用户

- 按场景脚本回答问题，例如"最大电平""能否改用线路""能否调低录音增益""能否提供参考录音"；
- 对每个建议都确认，除非脚本规定"做不到"。

### 7.3 场景

- **开发场景 30 个**，由我写。
- **留出场景 20 个**，沿用 D059 的做法：由 Cursor 只根据分布要求和动作说明来写，在模型提示词提交之前冻结，并记录 SHA-256。

### 7.4 评分

| 指标 | 含义 |
|---|---|
| 最终正确 | 结束状态正确；起始失真电平在真实值 ±3 dB 内（或正确判断为干净或无法测）；环境问题被识别并修正 |
| 轮数 | 平均用了几轮 |
| 多余轮数 | 超过"最少需要轮数"的部分 |
| 拒绝次数 | 被校验拦下并退回规则版的动作数 |
| pass^3 | 同一场景重复跑 3 次，三次都正确的比例（只对模型版有意义） |
| 打乱检验 | 把每轮的结果换成另一个场景的结果，模型版的最终正确率应明显下降。下降不明显，说明模型没在看反馈 |

## 8. 验收和上线规则

1. **规则版**
   - 留出场景最终正确率 ≥ 0.9 即可上线，作为测试会话的默认行为，不涉及模型。
   - 未达标就改规则或另起设计。规则版的修改同样要在冻结的留出场景上验收。
2. **模型版**，在留出场景上同时满足以下条件才能打开：
   - 最终正确率 ≥ 0.9，且 ≥ 规则版；
   - 平均轮数 ≤ 规则版 + 0.5；
   - pass^3 ≥ 0.8；
   - 打乱检验下最终正确率至少下降 30 个百分点；
   - 在"最终正确率"或"平均轮数"上**明显优于**规则版（正确率高至少 5 个百分点，或平均少用至少 0.5 轮）。否则结论是"规则版足够"，模型版不上线。这本身也是一个有效结果。
3. **人工抽查：** 10 个模型版会话的完整记录和汇总，不能有错误陈述。

## 9. 结果问答

- **入口：** 在任意一次结果（扫频或现成录音诊断）下面提问。API 为 `POST .../questions`，请求体是 `{"question": "..."}`。
- **模型输入：** 这次结果的解释材料包（§30）和用户的问题。
- **模型输出：** 1–4 句回答，每句带引用，或者明确拒答（`out_of_scope`）。
- **校验：**
  - 沿用 §30 的引用、数字、措辞和故障一致性检查；
  - 建议性的内容只能来自下一步菜单；
  - 不能推测证据里没有的原因，例如"是喇叭坏了"；需要推测时必须拒答，并说明缺什么测试。
- **失败或关闭时：** 返回固定的模板回答，指向报告里的相关条目，并记录原因。
- **开关：** 提示词 `v0.3-s1-qa-1.0`，开关 `SIGNAL_DIAG_QA_MODEL=enabled`，默认关闭。
- **验收：**
  - 题目：开发问题 40 个，加上 Cursor 写的留出问题 20 个。其中约四分之一是证据回答不了、应该拒答的问题。
  - 门槛：
    - 留出组校验通过率 ≥ 0.9；
    - 该拒答的问题拒答率 ≥ 0.9；
    - 人工抽查 20 个回答，错误陈述为 0。

## 10. 分阶段实施

每一阶段单独开 PR，都需要操作员授权合并。

1. **阶段 A：会话框架、规则版和沙盒**（不涉及模型）
   - 会话存储、动作结构和校验器、规则版、停止条件；
   - API `/api/v1/test-sessions`、CLI `session`、网页上的会话面板；
   - 沙盒设备和用户、30 个开发场景、评测脚本。
   - 留出场景由 Cursor 写好并冻结后，跑规则版验收。
2. **阶段 B：模型版**
   - 提示词、适配器、拒绝记录、`--live`；
   - 由 Cursor 跑真实模型验收，与规则版对比。
3. **阶段 C：结果问答**
   - 提示词、校验、API 和网页、评测脚本；
   - 留出问题冻结后，由 Cursor 跑验收。

## 11. 操作员决定

1. **先后顺序**
   - A（推荐）：A → B → C。先上线不依赖模型的规则版会话，再用模型去和它比，问答最后做。
   - B：先做问答（C），再做会话。
   - C：会话和问答并行。
2. **模型关闭时**
   - A（推荐）：测试会话照常可用，由规则版决定下一步。
   - B：只有模型打开时才提供测试会话。
3. **模型版上线门槛**
   - A（推荐）：按 §8，包括"必须明显优于规则版"和打乱检验。

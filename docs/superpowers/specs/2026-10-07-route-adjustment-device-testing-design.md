# 路线调整：面向设备测试的确定性诊断引擎与 LLM 测试向导（设计）

日期：2026-10-07
状态：已批准（操作员 2026-10-07，§7 四项均选 A / 批准；D052）。本文件只确定方向和阶段划分，不授权任何阶段的实现，也不授权任何真实模型运行。每个阶段开始前各自另写设计、合同增补和测试编号。
上位依据：AGENTS.md（Scope gates）、D004、D006、D016、D037、D045、D046、D050、D051。

## 1. 为什么调整

### 1.1 我们自己的证据

- **诊断本身，LLM 选工具没有带来准确性：**
  - 规划消融研究 `study_s1_planner_ablation_dev_1` 的机器结论是 `fixed_pipeline_dominance`（未正式采纳）。
  - 智能体增量研究（D045）在 T2 局部故障上，agent 和穷举分段扫描都是 18/24，增量为 0。agent 只是工具调用更少（96 次对 824 次）。
  - D049 修正基频之后，固定流程在 H1 留出集 T2 上 24/24 全对。
- **LLM 有可测出的价值的地方：** 把自由文字描述转成结构化上下文。T1 首稿全对，agent 22/24，关键词解析 17/24，增量 +5。
- **DSP 很便宜：** 30 秒立体声文件的全量分段扫描约 2–9 秒（D050、D051 实测），少调用几次工具没有实际收益。
- **只分析现成录音有原理上的上限：** EGFxSet 检查显示，合唱和移相这类不失真的处理，会在逐窗比较中伪装成谐波增长（D051 附录）。
- **真实录音上 planner 不稳定（`egfxset_live_1`，26 个配对，各跑一次，产品 prompt v9.11）：**
  - 9/26 次运行以 `max_planner_retries` 报错结束，没有结论。原因都是 planner 反复提出不成立的削波 claim（“clipping claim lacks one coherent evidence family”），被运行时校验驳回 3 次。
  - 只有 1/26 认定了谐波失真（BluesDriver 2-0）。确定性整文件门判定有谐波增长的 RAT 3-12 和 RAT 4-12，planner 都以报错结束。
  - 合唱和移相对照没有显示任何谐波区间，D051 的隐藏机制按设计生效。
  - 同样的配对，确定性引擎每次都能给出结论，不会因为重试耗尽而失败。

### 1.2 外部做法（2026-10-07 调研）

- **专业测量软件**（REW、Klippel、SoundCheck）：让设备回放扫频或步进正弦等受控激励，跑固定分析。准确性来自激励设计，不来自动态选工具。
- **音频质检和修复产品**（iZotope RX Repair Assistant、Pulsar、BATON）：所有检测器全量运行，列出带时间位置的问题，没有 planner。
- **端到端音频大模型：** 在音高、响度这类基础物理属性上多数接近随机，不能直接用来测量（SonicBench、AudioJudge 等）。
- **测量行业对 LLM 的用法：** 把工程师的自然语言转成测试脚本（例如 Rohde & Schwarz CMX500 AI Scripting Assistant），不让模型决定判定结果。

### 1.3 结论

确定性 DSP、版本化规则、证据可追溯，这些保留。“LLM 选择调用哪个 DSP 函数”这一层没有证据支撑，应该移除。LLM 移到能证明价值的两端：理解用户、解释结果。另外，用受控激励换取测量准确性。

## 2. 产品定位（操作员 2026-10-07 选定 A）

**目标用户：** 测试音频设备的工程师和懂一点的用户（功放、耳机、音箱、声卡、车载音响），他们能按要求回放测试信号并录回。

**要回答的问题：** “这台设备为什么听起来失真？问题出在哪里，下一步怎么查？”

**差异点：** 不在测量算法（采用业界标准方法），而在于把整条链路做通：

```text
用户的模糊描述
  → LLM 判断该做什么测试并引导操作（向导）
  → 用户回放标准测试文件并录回
  → 确定性引擎测量并由规则判定（引擎）
  → LLM 用人话解释结论和下一步（解释）
```

每句解释都能追溯到同一次运行的证据和规则判定。现有工具只覆盖其中一段：REW 和 Klippel 测得准但难读，iZotope 修音但不诊断设备，通用聊天模型讲人话但听不准。

**不做：** 面向任意录音的“看病”（选项 B）、更多故障类型的 ML 检测器、实时测量和声卡直连（继续沿用“上传 WAV”）。

## 3. 目标架构

```text
signal → dsp → tools → rules/knowledge → engine → explain/guide → app
```

| 层 | 职责 | 是否用 LLM |
|---|---|---|
| 引擎（engine） | 按测试方案全量运行检测器，由规则得出结论和定位 | 否 |
| 解释（explain） | 把结论、证据和规则判定讲成人话，给出下一步 | 是，但只能引用已有证据，不能产生结论 |
| 向导（guide） | 理解描述，追问缺失信息，推荐测试方案和操作步骤 | 是，输出必须由用户确认（沿用 D047） |

**不变的原则：** 原始波形和完整 FFT 不进模型；数值只来自确定性 DSP；阈值只来自版本化规则；结论只来自规则；缺少凭据时不静默退回桩实现。

## 4. D004 的改写

**原文：** S1 不要求固定流程，产品 Agent 选择第一个工具、检查观测、必要时重新规划、证据足够时停止。

**拟改为（D052）：** 产品的动态选择发生在测试方案层面（做什么测试、问用户什么、如何解释），不在 DSP 函数调用层面。诊断核心是确定性引擎，按方案全量运行检测器并由规则判定。

V0.2 的 79/80 和所有已记录研究保持原样，它们是 D004 原路线下的历史证据。

## 5. 阶段划分

各阶段按顺序排列，每个阶段单独设计、单独审批。

### 阶段 1：确定性诊断引擎成为产品默认

- 以现有的 `ContextualFixedPipelineBaseline`（规则门与产品相同）为基础，加上 D050/D051 的分段扫描，组成产品引擎。三种模式下全量运行，结论、claims、证据引用的格式与现有报告一致。
- LLM planner 路径（v9.11）不再是默认，代码和身份保留，用于对比和历史复现（见 §7 决策 2）。
- 不调用模型。可以完全离线验证：在已有的研究用例上对比引擎和 v9.11 已记录的结果。

### 阶段 2：扫频激励测试

- 产品生成标准测试文件：指数扫频，带同步标记，可选多个电平。
- 用户回放并录回后，引擎对齐并反卷积（Farina 方法），分离线性响应和各阶谐波；按频率和电平给出 THD 和各阶谐波，指出失真从哪个频率或电平开始。
- 新增版本化规则 profile，阈值仍为演示值，并明确标注。
- 线性处理（EQ、合唱、移相）在原理上与谐波失真分开，用合成设备模型和 EGFxSet 类数据验证。

### 阶段 3：解释层

- 输入：引擎结论、证据和规则判定的紧凑摘要。输出：分段的人话解释和下一步建议。
- 每句话必须引用证据或判定编号，提到的数值必须与证据一致，不一致就拒绝输出并回退到确定性模板。这是“回退到模板”，不是回退到桩 planner。
- 需要真实模型评测，交给 Cursor 运行。

### 阶段 4：测试向导

- 在 D047 自由文字理解的基础上，推荐测试方案（测哪些电平、是否需要参考、用哪个测试文件）和操作步骤（接线、录音设置）。
- 用户确认后才执行，沿用 D047 的确认机制。
- 需要真实模型评测，交给 Cursor 运行。
